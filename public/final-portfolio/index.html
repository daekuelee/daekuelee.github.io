DirectX12 Rendering Core

DX12에서 어려웠던 것은 화면에 그리기 위해 많은 것들이 필요하다는 것이었습니다. 1. CPU가 기록한 command와 GPU가 실제로 소비하는 resource lifetime이 서로 다른 시간축에 있다는 점(비동기로 동작하기 때문에)에서 오는 이해의 어려움. 2. DX11에서 driver/runtime이 비교적 숨겨주던 descriptor binding, resource state, synchronization 문제가 DX12에서는 root signature, descriptor table, barrier, fence 같은 명시적 계약으로 드러남(보다 하드웨어적). 3. Swapchain/back buffer는 단순 화면 버퍼가 아니라 GPU가 쓰고 present 경로로 넘기는 resource입니다(같은 데이터를 읽는 방식을 바꿔주기 위한 transition 필요). 4. frame 단위로 재사용되는 command allocator와 upload memory는 fence 기준으로 안전성을 판단해야 했습니다.

그래서 FrameContextRing은 frame id와 fence를 기준으로 command allocator와 per-frame resource의 재사용 시점을 관리하도록 만들었습니다.

UploadArena는 프레임별 allocation count, bytes, peak offset, tag를 HUD에서 확인할 수 있는 디버깅 장치로 두었습니다. DescriptorRingAllocator와 ResourceStateTracker는 descriptor reuse와 resource barrier가 여러 render pass 사이에서 흩어지지 않도록 분리했습니다.

Shader 쪽은 HLSL 파일 하나의 문제가 아니었습니다. CPU 쪽 root parameter, descriptor table, constant buffer layout, structured buffer, PSO, HLSL register, matrix convention이 모두 맞아야 shader가 의미 있는 데이터를 소비할 수 있었습니다. 이 때문에 shader를 GPU-side ABI consumer로 보고 row_major matrix convention과 binding slot을 명시적으로 정리했습니다.

Kinematic Character Controller(KCC) / SceneQuery Deep Debugging

DX12EngineLab에서 가장 오래 붙잡은 부분은 capsule 기반 Kinematic Character Controller(KCC)와 SceneQuery였습니다. 여기서 seam은 cube의 경계나 접합부에서 capsule이 끼이거나, wall contact와 floor support의 의미가 섞이는 지점을 말합니다. 처음에는 seam이나 wall contact에서 캐릭터가 위로 뜨는 현상을 단순 normal 계산 문제로 봤지만, 재현 케이스를 쪼개 보니 normal마다 시맨틱이 다르며, 그 시맨틱을 정의해줘야 된다는 것을 깨달았습니다.

sweep hit normal, overlap recovery normal, floor support normal은 모두 Vec3처럼 보이지만 같은 의미가 아니었습니다. 여기에 StepUp, StepDown, 또한 KCC의 policy를 정확히 시맨틱으로 분리해야 하며, 외재적으로 정확히 정의한 뒤 진행해야 된다는 것을 깨달았습니다. 그렇지 않으면 walking/falling mode, velocity writeback, post-sweep cleanup이 분리되지 않은 채로 안에서 섞이고, 작은 patch 하나가 다른 버그를 만드는 구조가 됐습니다.

특히 near-zero hit, skin, float penetration, initial overlap은 물리 쪽에서 계속 드러나는 문제였습니다. Analytic하게 sweep을 구현해도 실제 게임 루프에서는 contact offset과 수치 오차 때문에 겹침이 생기고, 이때 recovery/depenetration을 위한 MTD-like policy가 필요했습니다. 그래서 시각적 debug, HUD, frame-zone logging, trace 없이 KCC 버그를 눈으로만 따라가려 하면 원인 stage를 놓치기 쉬웠습니다.

PhysX는 geometry query, sweep, overlap, MTD, CCT recovery mechanics의 reference로 보고, Unreal은 CharacterMovement의 floor finding, walking/falling, landing policy를 비교했습니다. 결론은 단순했습니다. SceneQuery는 raw geometric facts를 제공하고, KCC는 movement policy를 소비해야 합니다. 이러한 경험이 float에서의 수치 안정성의 중요성(skin), 그리고 어떻게 디버깅해야 되는지(frame-zone-logging, depenetration과 같은 보정 등)를 익히게 하였습니다.

Collision Math / Query Background

Collision 쪽은 생각보다 훨씬 많은 기본기가 필요했습니다. Erin Catto 자료와 collision reference를 보면서 line, vector, triangle, AABB intersection, barycentric coordinates, parameter form, linear equation으로 접촉을 푸는 사고부터 다시 정리했습니다. Normal도 단순 방향 벡터가 아니라, 어떤 query가 어떤 feature에서 만든 normal인지가 중요했습니다.

Sweep과 CCD를 공부하면서, 충돌은 단순히 “겹쳤는가”가 아니라 “움직이는 도형이 언제 처음 닿는가”의 문제라는 것을 다시 보게 됐습니다. TOI는 continuous collision detection에서 움직이는 shape의 earliest impact를 나타내고, CSO, Minkowski sum/difference, support mapping은 GJK와 같은 solver의 이론적 배경 혹은 4차원(시간축 포함) 문제를 더 쉬운 구조로 바꾸어 풀게 해주는 배경이 되었습니다.

이미 겹친 상태는 또 다른 의미를 가졌습니다. Sweep hit은 미래의 접촉을 찾지만, MTD는 현재 penetration에서 최소 이동으로 빠져나오는 recovery semantic입니다. 이 둘을 같은 normal로 처리하면 KCC에서 wall-climb, upward pop, stuck이 쉽게 발생했습니다(MTD-like recover로 해결). 모든 primitive를 검사할 수 없기 때문에 broadphase/midphase가 필요했고, 여기서 BVH와 BVH4가 candidate를 줄이는 구조로 연결됐습니다.

이 배경은 DX12EngineLab에서 SceneQuery, KCC, BVH4 prototype의 책임 경계를 잡는 기준이 됐습니다. 또한 CSO, Minkowski, support mapping, GJK 계열 사고가 sweep과 convex query를 이해하기 위한 배경이 되었습니다.

Webserv - C++98 / POSIX 기반 비동기 HTTP 서버
github.com/42-webserver/webserv
C++98 POSIX epoll/kqueue Parser State Machine LRU Cache Trie Custom Buffer

Webserv는 third-party 라이브러리 없이 C++98, 시스템 콜, STL만으로 HTTP server / reverse proxy / CGI / non-blocking I/O를 구현한 프로젝트(nginx 하위 호환격)입니다. 코드 규모가 커질수록 모듈화, 확장성을 신경 써야 된다는 것을 배웠으며, 기능 추가보다 event loop, connection lifetime, parser state, buffer lifetime, file cache가 서로 엉키지 않게 만드는 일이 중요했습니다.

초기에는 웹서버를 어디서부터 설계해야 할지 막막했기 때문에 RFC, HTTP 자료, nginx source, kernel source를 같이 보며 event-driven server 구조를 분석했습니다. 이를 바탕으로 epoll/kqueue 추상화, parser state machine, 4KB head와 64KB linked block 기반 buffer, LRU cache, multi-read file management를 구현했습니다.

C++98 제약 안에서 custom shared_ptr, hash table, trie, optional 같은 도구를 직접 만들며 자원 소유권과 lifetime을 코드 구조로 표현하는 경험을 했습니다. 이때부터 큰 코드베이스를 읽고, 시스템 호출과 자료구조, 객체 구조를 같이 맞추는 훈련을 했고, 이 감각은 DX12의 explicit resource/control model을 이해하는 기반이 됐습니다.

React from Scratch - Fiber / Scheduler / Render-Commit 분석
github.com/42ForYou/RFS
JavaScript Fiber Scheduler Render / Commit Split Source Analysis

RFS는 단순 miniReact가 아니라, 큰 코드베이스에서 핵심 loop와 stage boundary를 찾아내는 훈련이었습니다. React v16 source를 직접 읽으며 recursive render를 interruptible work loop로 바꾸는 구조, Fiber double buffering, scheduler, Synthetic Event, render/commit split을 추적했습니다.

Fiber에서 흥미로웠던 점은 업데이트를 하다가 멈추고, 브라우저에 제어권을 넘겨준 뒤, 다시 이전 작업 지점부터 이어서 진행할 수 있다는 점이었습니다. 이를 위해 재귀적 렌더링을 명시적 work loop와 unit of work로 바꾸고, scheduler가 우선순위와 시간을 기준으로 work를 나누는 구조를 이해해야 했습니다.

여기서 배운 것은 “중간 상태를 언제 멈춰도 되는가”, “언제 commit해도 되는가”, “어떤 stage가 어떤 상태를 소유하는가”였습니다. 이 사고방식은 이후 DX12 frame lifecycle과 KCC pipeline을 phase별로 나누어 디버깅하는 방식으로 이어졌습니다.

AI-Native Engineering Workflow

Claude Code와 Codex를 실제 EngineLab 개발에 써보면서 느낀 것은, AI가 강력할수록 개발자의 역할이 줄어드는 것이 아니라 오히려 semantic boundary, test harness, reference evidence를 더 정확히 정의해야 한다는 점이었습니다. 최신 AI는 긴 로그와 큰 코드베이스를 빠르게 정리하고 그럴듯한 patch를 만들 수 있지만, KCC/Collision처럼 sweep, recovery, grounding, mode transition이 얽힌 코드는 “한 번에 고쳐줘”로 맡기면 쉽게 산으로 갑니다.

그래서 저는 AI를 통한 코딩을 진행하며 실제 AI-ready codebase(SSOT가 정확히 명시, AGENTS.md를 통한 지도 제공 등)의 필요성 및 구현, skill, multi-agent, harness 등을 쓰는 등 AI 시대의 개발자로서의 훈련을 진행하였습니다. Repo-local AGENTS.md로 행동 규칙과 map을 고정하고, docs/audits/에는 문제를 파일 단위와 semantic 단위로 분리해 기록했습니다. 또한 거대 코드베이스 분석 시에도 사용하며 docs/reference/에는 PhysX / Unreal raw source 기반 contract를 남기고, local skill로 reference mining과 SceneQuery invariant audit을 반복 가능하게 만들었습니다.

NotebookLM은 DirectX12, graphics, collision reference를 RAG처럼 묶어 학습 속도를 올리는 데 사용했습니다.

이 경험을 통해 vibe coding은 빠른 프로토타입에는 유용하지만, 엔진 코드는 SSOT, acceptance criteria, rollback point, deterministic test가 없으면 금방 무너진다는 것을 배웠습니다. AI-ready codebase를 만들려면 암묵적인 semantic을 문서와 test로 끌어내야 하고, 개발자는 AI가 낸 답을 조타수처럼 계속 방향 조정해야 합니다.
