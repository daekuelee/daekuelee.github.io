② Flash and the FTL: what the chip cannot do, and how the SSD hides it

Page ① ended on one property of the hard disk: sector n is a fixed spot, and a rewrite simply overwrites it. Flash cannot overwrite. This page builds up why, from the cell, and then follows the SSD's answer: keep showing the OS the same sector array, but write every new version somewhere new and keep a map of where each sector currently lives.

An SSD has no motor, no platter and no arm (Figure 1). It is a circuit board with flash chips that hold the data, a controller chip that runs the drive's firmware, a little working memory for that firmware, and a connector that speaks the same sector interface as the hard disk of page ①. OSTEP describes the inside the same way: flash chips for persistent storage, some volatile memory such as SRAM for caching, buffering and mapping tables, and control logic. OSTEP 44.5

Because nothing moves, there is no seek and no rotation, which removes the cost that dominated page ①. The rest of this page is about the new costs that take its place.

Flash stores bits as electric charge trapped inside a transistor, called a cell, and the amount of trapped charge is read back as a binary value. A single-level cell (SLC) tells two levels apart and holds one bit. A multi-level cell (MLC) tells four levels apart and holds two bits, and a triple-level cell (TLC) eight levels and three bits (Figure 2, left). OSTEP 44.1

More levels per cell buy capacity and cost speed and lifetime, because the levels must fit into the same range of charge and each band gets narrower. OSTEP's numbers show both costs: programming a page takes 200–300 µs on SLC but about 900–1,350 µs on TLC, and SLC blocks are rated for about 100,000 erases against about 10,000 for MLC. SLC chips are faster and more expensive. OSTEP 44.1, 44.4, Figure 44.2

Cells are grouped at two sizes, and chapter 44 turns on the difference between them (Figure 2, right). A page is a few KB, typically 4 KB; it is the unit that is read, and the unit that is written (flash calls writing "programming"). A block, also called an erase block, is typically 128 KB or 256 KB, so it holds 32 to 64 pages; it is the unit that is erased. Many blocks form a plane, which OSTEP also calls a bank, and a chip has several planes. OSTEP 44.2

The words clash with older ones, and OSTEP warns about it: a flash block is not a file-system block, and a flash page is not a virtual-memory page. On these pages "block" and "page" mean the flash units, and "logical block" means the sector-array number the OS uses. OSTEP 44.2, tip on terminology

A flash chip offers exactly three operations, and they are not symmetric. Read takes a page number and returns that page. Erase takes a block and sets every bit of every page in it to 1, destroying whatever the block held. Program takes an erased page and writes data into it, but it can only change 1s into 0s. OSTEP 44.3

These two rules force everything else. Writing a new value into a page that already holds data would need some bits to go from 0 back to 1, and only an erase can do that. An erase, though, works on a whole block. So a page, once programmed, cannot be programmed again until its entire block has been erased. OSTEP 44.3

OSTEP keeps track of this with a state per page (Figure 4, top). A page starts INVALID (i): its contents are unknown and it cannot be programmed. Erasing its block makes it ERASED (E), ready to program. Programming it makes it VALID (V), and only then should it be read. Programming a VALID page a second time is an error. The only way back to ERASED is to erase the whole block, which resets every page in it. OSTEP 44.3

Figure 4, bottom, runs OSTEP's example with unrealistically small 8-bit pages. ① A 4-page block holds four VALID pages, and the client wants page 0 to become 00000011. ② The block must be erased first, and the erase sets all 32 bits to 1, in all four pages. ③ Programming page 0 now works; it turns exactly the needed 1s into 0s. But pages 1, 2 and 3 are gone. To change one page without losing its neighbours, the neighbours must first be copied somewhere else, into memory or into another block. OSTEP 44.3, "A Detailed Example"

This is the root of chapter 44. On a hard disk, "write sector n" was one operation on one unit (page ①, §3). On flash it becomes two operations on two different sizes: erase a large block, then program a small page, once.

Figure 5 shows what the three operations do to the cells, and with it why an erase gives 1s and why program goes only one way. ① A read puts a read voltage on the chosen word line and a higher pass voltage on all the others, so every other cell of a string conducts whatever it holds. Current then flows down the string only if the chosen cell conducts as well. An empty cell conducts and reads as 1. Trapped electrons raise the voltage a cell needs before it conducts, so a charged cell blocks the current and reads as 0. An erased page is empty, so it reads all 1s: the 1 is the empty state, not a value the erase writes. ② A program puts about 20 V on the chosen word line, and under it electrons tunnel from the channel into the charge trap. The choice is made cell by cell through the bitlines: a string held at 0 V is programmed, while a string held high lifts its own channel's voltage, which cancels the pull and keeps the electrons out. A gate at a strong positive voltage can only pull electrons in, so program can only add charge, and adding charge only turns 1s into 0s. ③ An erase reverses the field. The word lines go to 0 V and about 20 V goes onto the body under the strings, which pushes the electrons back out. That body is shared by every string of the block, so every cell of the block empties at once. Shielding the other pages of each string from that voltage is possible only at extra cost and stress, so chips erase whole blocks. OSTEP 44.1, 44.3; Branch Education 7:06–7:58

④ The same question, asked at seven read voltages, gives a TLC cell its three bits. An empty cell conducts at all seven and a full one at none, and the video labels the levels by that count, from 111 for empty to 000 for full: that is why more charge reads as a smaller number. Real chips assign the bit patterns in Gray code instead, so that neighbouring levels differ in one bit and a small drift in charge costs one bit error, not several. Branch Education 7:06–7:20

Figure 6 answers why the chip allows only one program per page between erases, even though a second one could still clear bits. ① New data is an arbitrary bit pattern, and almost any pattern needs some 0 to become 1, which only an erase does. ② Even a change that only clears bits breaks the page. Each page carries an error-correcting code (ECC) in its spare bytes, computed over the whole page and checked on every read. Changing one data bit changes the code in many places, some of them from 0 to 1. ③ Every program pulse puts a high voltage on cells it did not choose, and the protected cells on the same word line and the cells on the word lines beside it gain a little stray charge. OSTEP calls this program disturb, and it is why SSDs program the pages of a block once each, in order, from low to high. ④ In MLC and TLC one cell carries bits of two or three pages, so reprogramming one page would move cells whose level the other pages also read. NAND datasheets state the rule as NOP, the number of partial programs allowed per page: 1 for MLC and TLC. Old SLC chips allowed up to 4, but each partial program filled a different, still-erased part of the page, such as one 512-byte sector with its own ECC, so no bit was programmed twice. OSTEP's model keeps only the rule: programming a VALID page is an error. OSTEP 44.3–44.5

CARRYEmpty cells conduct, so they read 1, and an erase empties a whole block through the body its strings share. Program pulls charge into chosen cells of one page, turning 1s into 0s, once per page; a second pass would break the page's ECC and disturb its neighbours. So a page cannot be rewritten in place: changing it means erasing its whole block, after rescuing the other pages in it.

Reading a page takes tens of microseconds: 25 µs on SLC, 50 on MLC, about 75 on TLC (Figure 7). That is roughly a hundred times faster than a hard disk's random read, and it barely depends on where the page is or where the previous request went. Flash is therefore a random-access device, like memory and unlike a disk. OSTEP 44.3–44.4, Figure 44.2

Programming a page takes hundreds of microseconds, from 200–300 µs on SLC up to about 900–1,350 µs on TLC. One chip writing one page at a time would be slow, so SSDs program many chips in parallel to reach good write bandwidth. OSTEP 44.4

Erasing a block takes milliseconds: 1.5–2 ms on SLC, about 4.5 ms on TLC. That is the size of a hard-disk seek, the very cost the SSD was supposed to remove. The design goal for everything that follows comes from this bar: erase rarely, and never make a client's write wait for an erase. OSTEP 44.4

In CPU cycles the same times read as the memory hierarchy continued downwards (Figure 8). At 3 GHz one microsecond is 3,000 cycles. An L1 hit is about 4 cycles and a DRAM access about 300. A flash page read is 75,000–225,000 cycles, the cost of 300–900 DRAM misses; a program is about a million cycles; an erase is about ten million, the size of a hard disk's random read at 18–40 million. A cache miss is short enough that the core simply stalls until the data arrives. A flash read is not: the thread that issued it gives up the core and the OS runs another thread, because a switch costs a few microseconds while the read costs tens. For the fastest SSDs that boundary blurs, and kernels sometimes poll the device instead of sleeping. Wear. Each program/erase cycle leaves a little extra charge trapped in the cells. As it builds up, a 0 gets harder to tell from a 1, and at some point the block can no longer be used. Manufacturers rate MLC blocks at about 10,000 program/erase (P/E) cycles and SLC blocks at about 100,000, though measurements have found real lifetimes longer than rated. A block is a consumable: every erase spends some of it. OSTEP 44.4

Figure 9, left, shows where the extra charge goes. ① Program and erase both drive electrons through a thin insulator at high voltage. Each pass damages the insulator a little, and some electrons stay stuck in it, and an erase does not reliably clear them. ② Figure 9 ② counts the cells at each switch-on voltage, one hump for the 1s and one for the 0s. The stuck charge raises the switch-on voltage of erased cells, and the damaged insulator lets charged cells leak electrons, which lowers theirs. Every cell is hit by a different amount, so both humps widen toward each other. Once the two ranges overlap, some cells fall on the wrong side of the read voltage and their bits read wrong. The page's ECC repairs a few such bits; when the errors pass what it can repair, the block is retired. TLC wears out sooner, in a few thousand cycles, because its eight ranges are narrow to begin with. This is the lifetime half of write amplification (Figure 11, ④) and the reason for wear leveling on page ③. OSTEP 44.4 (the extra charge); where it sits and the TLC figure: beyond OSTEP

What the SSD does about it. Wear is physics and cannot be removed, so the SSD works around it in three ways (Figure 9, ⑤). a. It erases less. The log-structured FTL writes each new version of a page to a fresh page, so a write no longer costs an erase; erases happen only when garbage collection reclaims a block (§7). The live pages that collection has to copy are write amplification, and the lower it is, the fewer erases (③ §3–§4). b. It spreads the erases. The FTL counts erases per block and writes to the least-worn blocks. Blocks holding cold data are never erased, so now and then the FTL moves that data onto a worn block and puts the fresh one back into use (③ §8). c. It catches what is left. ECC repairs a few bad bits per page; a block past that is retired, and hidden spare flash takes its place (③ §4, overprovisioning). Without these, the fixed mapping of §6 erases a block on every rewrite: a page rewritten ten times a second spends a 10,000-erase block in about 17 minutes. With them, a drive can take about capacity × P/E cycles ÷ WA of writes over its life. Makers state this as TBW (terabytes written): about 600 TB for a typical 1 TB TLC drive. OSTEP 44.6 (fixed mapping wears blocks out), 44.10 (wear leveling); the 17 minutes, the formula, TBW and spare blocks: beyond OSTEP

Disturbance. Reading or programming one page can flip bits in neighbouring pages; these are called read disturbs and program disturbs. To limit program disturbance, SSDs program the pages of an erased block in order, from the lowest page to the highest. OSTEP 44.4–44.5

Figure 9, right, shows both. ③ A read puts the pass voltage on every other word line of the block (Figure 5, ①), so each read lets a tiny amount of charge creep into cells it did not ask for. One read does no harm. Many thousands of reads of one block can flip bits, so controllers count reads per block and copy a heavily read block somewhere fresh before that happens. A program, at about 20 V, does the same thing harder (Figure 6, ③). ④ Programming a page also shifts the page next to it slightly. Written in order, from low to high, each finished page is shifted once, when the page above it is written, by an amount the chip expects and corrects for. Written in any order, a finished page can be shifted from both sides, at times nobody planned for. Of disturbance, one rule is carried forward: within a block, pages are programmed in order, which the log-structured FTL of §7 does naturally. OSTEP 44.4–44.5; read counting and the in-order correction: beyond OSTEP

A hard disk has none of these limits. It fails mechanically, the worst case being a head crash, where the head touches the surface, but rewriting a sector a million times costs it nothing. OSTEP 44.4

CARRYRead: tens of µs, about 100,000 cycles or hundreds of DRAM misses, anywhere (random access). Program: hundreds of µs. Erase: milliseconds, as slow as a seek. A block survives about 10,000 erases (MLC), because charge stuck in its insulator blurs 1s and 0s. So erase rarely, and spread the erases over all blocks. Of disturbance, keep one rule: program a block's pages in order.

The file system above still speaks the interface of page ①: read or write sector n, and overwriting is allowed. It was written for hard disks, and the SSD is meant to drop in under it unchanged. OSTEP presents this as a choice for backwards compatibility: a stable interface between two layers lets each side change on its own, at the price that an interface designed for one generation can fit the next one badly. OSTEP 44.5 and its tip on backwards compatibility

The part of the SSD that bridges the gap is the flash translation layer (FTL): firmware in the controller that takes reads and writes of logical blocks and turns them into reads, erases and programs of physical pages and blocks (Figure 10). It is asked for good performance and long life at once. OSTEP 44.5

For performance, two things matter. The first is to use many flash chips in parallel, which every modern SSD does. The second is to keep write amplification low. A page cannot be overwritten (§3), so the FTL often programs more than the client sent: the new data, plus old pages it has to move to make room. Write amplification (WA) measures that excess: the bytes the FTL programs into flash divided by the bytes the client asked to write (Figure 11). ① The client writes 4 KB. ② Behind it, the FTL programs 16 KB, the new page and three old pages moved along with it, so WA = 16 ÷ 4 = 4. WA = 1 would mean no extra writes at all. Reads the FTL makes on the way do not count, because reads do not wear blocks. OSTEP 44.5

The extra bytes cost twice. ③ Now: the client's write waits for four programs instead of one, 0.8–5.4 ms instead of 0.2–1.35 ms. ④ Later: every programmed byte spends block life. A page can be programmed only once per erase (§3), so the erase limit of §4 is also a budget of programs: a 1 TB drive whose blocks survive about 10,000 erases can program about 10,000 TB over its whole life, and no more. The flash cannot tell the client's bytes from moved ones, so both come out of the same budget. At WA = 1 all 10,000 TB is client data. At WA = 4 every 4 KB the client writes spends 16 KB, so the client gets a quarter, 2,500 TB, and the other 7,500 TB goes to moved pages; the same drive wears out after a quarter of the client writes. §6 traces this on one block, write by write (Figure 12, ④), and page ③ shows the main source of WA in real SSDs, garbage collection; page ③, Figure 3 ② counts this same budget one GC cycle at a time, one erase per cycle. OSTEP 44.4–44.5

For lifetime, two things matter as well. The first is wear leveling: spreading erases evenly over all blocks so that they wear out at about the same time, instead of a few popular blocks dying early. The second is programming the pages of each block in order, to limit disturbance. OSTEP 44.5

So the FTL has one question to answer before anything else: when the OS writes logical block n, which physical page should hold it?

CARRYThe FTL is firmware in the SSD's controller that turns "read or write sector n" into page reads, page programs and block erases. Its goals: chips in parallel, low write amplification (bytes programmed ÷ bytes the client wrote; each extra byte costs program time now and block life later), and even wear.

Why not keep logical page n on physical page n?

main · read

Figure 12. Direct mapping (OSTEP 44.6), traced on a toy 4-page block. Rewriting one page costs the whole block: a read of every page, an erase, and a program of every page. The red box counts the two failures, speed and lifetime. ④ The same write repeated until the block wears out: its 40 programs carry 10 client pages under direct mapping, against 40 if nothing had to move.

The simplest FTL copies the hard disk: logical page n always lives on physical page n. OSTEP calls this direct mapping. Reads are easy, since a read of logical page n is a read of physical page n. OSTEP 44.6

Writes are the problem, because physical page n is already programmed and cannot be programmed again (§3). Figure 12 follows a write of logical page 1 into a 4-page block that holds a, b, c and d. ① The FTL reads the whole block into memory and replaces b with b′. ② It erases the block. ③ It programs all four pages back, in order. OSTEP 44.6

Count the cost. One 4 KB client write became 4 page reads, 1 block erase and 4 page programs, so WA = 4. With realistic 256 KB blocks of 4 KB pages, WA is 256 ÷ 4 = 64, and every single write also waits for a millisecond-scale erase. OSTEP's verdict is that direct mapping writes more slowly than a hard disk, seeks and rotations included. OSTEP 44.6

Lifetime fails too, and Figure 12, ④ shows how. Each erase lets every page of a block be programmed once more, so a block's erase limit is also a limit on programs: a toy block that survives 10 erases holds 4 × 10 = 40 page programs in its life. Under direct mapping each one-page client write spends 4 of them, 1 for the new page and 3 for old pages moved along, so the block wears out after 10 client writes. Had the client rewritten all four pages each time, nothing would have needed moving, and the same 40 programs would have carried 40 client pages. The block dies after the same 10 erases either way; WA decides only how much of its life reaches the client, because the flash cannot tell client bytes from moved ones. Scaled up, this is Figure 11, ④: a 1 TB drive whose blocks last about 10,000 erases can program about 10,000 TB, and at WA = 4 the client gets 2,500 TB of it. With real 256 KB blocks direct mapping has WA = 64, so the client would get about 1/64, some 156 TB. OSTEP 44.6; the budget arithmetic: beyond OSTEP

A second problem sharpens the first. File systems rewrite some blocks far more often than others; their own metadata is the usual example. Under direct mapping every rewrite of a popular logical block erases the same physical block, which dies after its ~10,000 cycles while the rest of the chip is nearly new. The workload, not the FTL, decides which blocks wear out. OSTEP 44.6

Both failures have one cause: tying a logical block to one physical place, the very property that served the hard disk well (page ①, Figure 4).

CARRYDirect mapping (logical n = physical n) turns each small write into read, erase and program of a whole block (WA = 4 on the toy block, ≈ 64 on real ones). Every program spends the same erase budget, so the client gets only 1/WA of each block's life, and hot blocks burn out first. The fixed link between address and place has to go.

§7

The log-structured FTL: how does writing somewhere new solve both failures?

★ core · read every line

Figure 13. The SSD version of page ①'s Figure 6. The OS sees the same array of numbers. Behind it, the FTL's map says where each number currently lives; a rewrite of logical block 100 programs a fresh page and moves the map entry, so the place changes on every write.

The fix gives up the fixed place (Figure 13). When the OS writes logical block n, the FTL does not go back to where n was. It writes the data into the next free page of the block currently being filled, and records in a mapping table, usually just called the map, that n now lives there. Writing in this append-only way is called logging, and an FTL built on it is log-structured; most FTLs today are. A read of n looks n up in the map and reads that page. OSTEP 44.7

The map does for the SSD what a page table does for virtual memory. A stable number goes in, the current physical location comes out, and the location can change without the user of the number ever noticing.

Figure 14 runs OSTEP's example. Blocks hold four 4 KB pages, every page starts INVALID, and the client writes 4 KB logical blocks. OSTEP 44.7

Step 1. The client writes logical block 100 with contents a1. The FTL picks physical block 0, but its pages are INVALID, so it first erases block 0. It then programs page 0 with a1 and records 100 → 0 in the map. The writes of 101 (a2), 2000 (b1) and 2001 (b2) go to pages 1, 2 and 3, in order, and the map gains three more entries. OSTEP 44.7

Step 2. The client rewrites 100 and 101 with c1 and c2. Direct mapping would now read, erase and reprogram block 0. The log-structured FTL instead erases the next block, block 1, and programs pages 4 and 5. The only other change is in the map: 100 → 4 and 101 → 5. A later read of 100 goes map → page 4 → c1. OSTEP 44.7–44.8

Figure 14. OSTEP's example (44.7–44.8, redrawn) with 4-page blocks. Step 1 fills block 0 in order and records four map entries. Step 2 rewrites logical blocks 100 and 101: the new versions go to the next free pages, 4 and 5, and only the map changes. Pages 0 and 1 now hold dead data that only an erase of block 0 can reclaim, while block 0 still holds the live b1 and b2.

Compare the two FTLs on the same rewrite. The log-structured one programs exactly the pages the client wrote, so at this moment WA is 1, and it erases once per block filled rather than once per write. Repeated writes to one hot logical block land on different physical pages, so their wear spreads over the chip. Both failures of §6 are gone. OSTEP 44.7

Surviving power loss. The map lives in the controller's volatile memory, yet an SSD that forgot its map would have lost every file. The simplest remedy stores, with every page, a note of which logical block it holds, in a small spare region next to the page called the out-of-band (OOB) area. After a power failure the controller scans the OOB areas and rebuilds the map. Scanning a large SSD is slow, so higher-end devices add logging and checkpointing to recover faster; page ④ shows the same two ideas inside a file system. OSTEP 44.7, aside on mapping persistence

CARRYA log-structured FTL writes every new version of logical block n to the next free page and updates a map n → page. A write costs one program, erases happen once per filled block, and wear spreads. The map is rebuilt after power loss from the OOB note on each page.

What does the log cost?

main · read

Figure 15. Chapter 44 as one chain. Red boxes are limits or failures, teal boxes are fixes, and amber lines name the problem each fix creates. The top row is this page; the three columns are page ③. Every box is a link.

Look again at Figure 14, step 2. Pages 0 and 1 still hold a1 and a2 and are still VALID to the chip, but no map entry points to them. They are garbage: dead data taking up space. Every rewrite leaves one more such page behind. A page can be freed only by erasing its whole block, and block 0 also holds the live b1 and b2, so the space cannot simply be taken back. OSTEP 44.7–44.8

OSTEP names two costs of the log-structured approach. Garbage forces garbage collection, which copies live data and so adds writes. And the map needs one entry per page, which for a large drive is a lot of memory. A third cost comes from wear: blocks full of data that never changes are never collected, so they never take their share of erases while the others wear down. Figure 15 draws the whole chain, with each fix creating the problem the next box solves; page ③ follows each column to its end. OSTEP 44.7, 44.10

CARRYThe log works, but it leaves garbage, needs a big map, and leaves cold blocks unworn. Each is a section of page ③, and garbage collection is the one that sets the price.
