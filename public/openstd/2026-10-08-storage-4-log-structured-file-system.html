④ The log-structured file system: write everything sequentially, then find it again

Page ③ ended on the fact that the SSD's log began as a file-system idea. In the early 1990s LFS applied it to a whole file system on a hard disk: gather every update, data and metadata alike, into one large segment and write it in a single sequential transfer. This page follows the design one problem at a time: how much to gather, how to find an inode that moves on every write, where the map of inodes lives, why directories do not trigger a cascade of updates, how old versions are cleaned, and how the system survives a crash.

Section tags: ★ core = read every line · main = read · skim = the figure and the CARRY line at the end of the section are enough. Paper tags: papers: needed = the OpenStd papers use it without explaining it · papers: skip = safe to pass on the way to the papers; nothing is cut. On the way to the papers: §1, §2, §7, §9, §11 and §12 are needed, the rest can be skipped. §12 is where this page meets the papers. Colors on this page: amber = data block, teal = inode, violet = piece of the inode map, red and struck = garbage.

§1

Why did LFS want every write to be sequential?

main · readpapers: needed

FOR THE PAPERS · NEEDEDThe bet itself: buffer small writes and send them as one large sequential write. A log-structured cache is this design with objects in place of file blocks; Flashield, CacheLib's large-object cache and Kangaroo's small log all append in large writes (page 3.5 §2). Why they append when flash has no positioning: §12.1.

Figure 1. The problem LFS attacks (OSTEP 43, introduction). Top: FFS keeps the six blocks of a new file in one block group, yet still pays a short seek and a rotation for each. Bottom: LFS writes the updates as one contiguous run, paying the positioning cost once.

Mendel Rosenblum and John Ousterhout designed LFS at Berkeley around four observations. Memories were growing. As more of the disk's contents could be cached in memory, reads were increasingly served from the cache, so the traffic reaching the disk was mostly writes, and file-system performance came to be decided by write performance. The random–sequential gap was growing. Page ① §2 showed transfer rates rising with bit density while seek and rotation improve slowly. OSTEP 43, introduction

Existing file systems wrote small things to many places. Figure 1, top, shows the Fast File System (FFS) creating a one-block file, which takes six writes: the new inode, the inode bitmap, the directory's data block, the directory's inode, the file's data block, and the data bitmap. FFS keeps all six in one block group, but each is still a short seek plus a rotation, and performance falls far below the disk's sequential bandwidth. File systems ignored RAID. On RAID-4 and RAID-5 a write of a single block costs four physical I/Os, the small-write problem, and file systems did nothing to avoid it. OSTEP 43, introduction

An ideal file system would therefore turn every write into a large sequential one. That is possible for writes and impossible for reads. A read must go wherever the requested block happens to be, but for a write the file system chooses the location, and LFS exploits exactly that choice. Its plan: buffer all updates in memory, metadata such as inodes included, and once enough have collected, write them to an unused part of the disk in one long sequential transfer. LFS never overwrites anything in place (Figure 1, bottom). OSTEP 43, introduction and crux

The log-structured FTL of page ② makes the same move for a different reason. The FTL writes somewhere new because flash cannot overwrite; LFS writes somewhere new because a hard disk is fastest when it never has to reposition.

CARRYLFS's bet: caches absorb reads, so make writes fast. Buffer every update, data and metadata alike, and write them in one large sequential transfer to free space. Never overwrite in place.

§2

Is writing in address order enough? Segments and write buffering

main · readpapers: needed

FOR THE PAPERS · NEEDEDThe segment: a large unit filled in memory and written at once. Kangaroo's log buffers one segment in DRAM before writing it, and FairyWREN makes each segment exactly one erase unit, so dropping a segment frees a whole unit with nothing to copy (Kangaroo §4.2, FairyWREN §5.2). More in §12.2.

Figure 2. Top: why order alone fails (OSTEP 43.2). Bottom: OSTEP's segment example. Four new blocks of file j and its inode, plus one new block of file k and its inode, go to disk together; each inode already points at addresses inside the same segment.

The basic move is simple. When a file gets a new data block D, LFS writes D and also the file's updated inode, which points to D, next to each other in the log. OSTEP draws D at address A0 and, right after it, the inode with its block pointer b[0] = A0. An inode is much smaller than a data block, around 128 bytes against 4 KB. OSTEP 43.1

Writing in address order is not enough by itself (Figure 2, top). Suppose LFS writes one block at address A at time T, and the next block, A+1, a little later, at T + δ. In between, the platter has turned, so A+1's spot has just passed under the head, and the second write waits for almost a full rotation, Trotation − δ. Consecutive addresses pay off only when they reach the disk as one large contiguous write. OSTEP 43.2

LFS therefore uses write buffering: it keeps updates in memory and writes them out only once it has enough of them. The chunk it writes at once is called a segment, a large-ish run of a few MB. Figure 2, bottom, is OSTEP's small example. Four data blocks of file j with j's inode, and one new block of file k with k's inode, are buffered together and written as a single seven-block segment. Each inode can point at addresses inside the same segment because LFS decides in advance where the segment will go. OSTEP 43.2

CARRYConsecutive addresses are not enough, because the platter keeps turning between small writes. LFS buffers updates in memory and writes one segment, a few MB, at a time.

§3

How much should LFS buffer before it writes?

★ core · the formulapapers: skip

FOR THE PAPERS · SKIPThe formula prices a hard disk's positioning time, which flash does not have. The papers size their writes by the erase unit instead (§2's line above), and the question becomes how many erase units can be open at once (§12.2).

Figure 3. The effective rate climbs fast at first and then crawls: each halving of the remaining gap to the peak doubles the buffer, the same shape as page ③'s 1/(1−u).

CLAIM

Suppose every write pays a fixed positioning cost Tposition and then transfers at the peak rate Rpeak. To reach an effective rate equal to a fraction F of the peak, with 0 < F < 1, each write must carry D = F/(1−F) × Rpeak × Tposition.

  1. One write of D takes Twrite = Tposition + D ÷ Rpeak.Positioning (seek plus rotation) first, then the transfer of D at the peak rate. OSTEP (43.1)
  2. The effective rate is Reffective = D ÷ Twrite = D ÷ (Tposition + D ÷ Rpeak).What was written, divided by the time it took. OSTEP (43.2)
  3. Ask for Reffective = F × Rpeak.So D ÷ (Tposition + D ÷ Rpeak) = F × Rpeak.
  4. Multiply both sides by the denominator: D = F × Rpeak × Tposition + F × D.The second term is F × Rpeak × (D ÷ Rpeak) = F × D.
  5. Collect the D terms: D × (1 − F) = F × Rpeak × Tposition, so D = F/(1−F) × Rpeak × Tposition.Dividing by 1 − F is allowed because F < 1. ∎
  6. OSTEP's example: Tposition = 10 ms, Rpeak = 100 MB/s, F = 0.9 gives D = 9 × 100 MB/s × 0.01 s = 9 MB.OSTEP leaves 95% and 99% as questions: F/(1−F) is 19 and 99, so 19 MB and 99 MB. OSTEP 43.3

The product Rpeak × Tposition has a plain meaning: it is the data the disk could have moved during one positioning delay, 1 MB in the example. To waste only 10% of the time positioning, each write must carry 9 times that. The factor F/(1−F) equals 1/(1−F) − 1, the same shape as page ③'s write amplification 1/(1−u), and Figure 3 shows the consequence: the last few percent of the peak are very expensive in buffer size.

CARRYD = F/(1−F) × Rpeak × Tposition. With 10 ms and 100 MB/s: 9 MB for 90% of the peak, 19 MB for 95%, 99 MB for 99%.

§4

How do you find an inode that never stays in one place?

★ core · read every linepapers: skip

FOR THE PAPERS · SKIPWhat returns is page ③ §5's idea: data that moves needs a map from a stable name to its newest place. Inodes themselves do not appear in the papers. §12.3 lines the imap up with the caches' DRAM index.

Figure 4. Top: in a classic UNIX file system, inode k's address is a calculation (OSTEP 43.4). Bottom: in LFS the inode moves on every update, so a piece of the inode map, written in the same segment, records where its newest copy is (OSTEP 43.5).

In a classic UNIX file system, finding an inode is arithmetic. The old UNIX file system keeps all inodes in one array at a fixed part of the disk, so the inode with number k sits at the array's start plus k times the inode size (Figure 4, top). FFS splits the array into chunks, one per cylinder group, which adds a lookup of the chunk's start address but is just as easy. OSTEP 43.4

LFS breaks this twice. Its inodes are scattered all over the disk, each written wherever its segment went. And because LFS never overwrites in place, every update of a file writes a new copy of its inode somewhere new, so the newest copy, the only one that matters, keeps moving. OSTEP 43.4

The fix is a level of indirection called the inode map (imap): a structure that takes an inode number and returns the disk address of the newest copy of that inode. It is naturally an array with a 4-byte disk pointer per entry, and whenever an inode is written, its imap entry is updated. OSTEP 43.5

The imap must survive crashes, so it has to be on disk too. Keeping it at a fixed location would bring the seeks back, since every update would be followed by a write to that fixed place. LFS instead writes the changed piece of the imap right next to the rest of the new data. Appending a block D to file k writes D, the new inode of k, and a piece of the imap together (Figure 4, bottom). The imap piece says inode k is at A1, and the inode says its block 0 is at A0. OSTEP 43.5

OSTEP attaches a tip here: many problems in computer science are solved by a level of indirection, from virtual memory to the very idea of a file, and the imap is a virtualization of inode numbers. Each level has an overhead, though, and as Wheeler said, the one problem indirection cannot solve is too many indirections. The imap plays the role of the FTL's map from page ②: a stable name goes in, a moving location comes out. OSTEP 43.5, tip on indirection

CARRYThe imap maps an inode number to the address of that inode's newest copy. Its changed pieces are written in the same segment as the data, so keeping it current costs no seek.

§5

Where does a lookup start, and how is a file read from scratch?

★ core · read every linepapers: skip

FOR THE PAPERS · SKIPThe checkpoint region and the lookup path are file-system machinery. The papers' caches find an object through a DRAM index or a hash of its key (§12.3).

Figure 5. The whole lookup chain (OSTEP 43.6–43.7, redrawn). The checkpoint region is the one thing at a fixed place; everything else is found through it.

One problem remains: the pieces of the imap are now scattered over the disk as well. Something must sit at a fixed, known place, or nothing could ever be found. LFS has exactly one such place, the checkpoint region (CR), at the start of the disk. The CR holds the addresses of the latest pieces of the imap. It is rewritten only periodically, about every 30 seconds, so it costs little performance. OSTEP 43.6

The on-disk structure is therefore a chain: the CR points to the imap pieces, the imap pieces hold the addresses of the inodes, and the inodes point to files and directories exactly as in a classic UNIX file system. A real LFS has a bigger CR (two of them, in fact, as §10 explains), many imap pieces, and many more inodes and data blocks than Figure 5 shows. OSTEP 43.6

Figure 5 reads a file from a cold start, with nothing in memory. ① Read the CR at its fixed address. ② Read every imap piece the CR points to, and keep the whole imap cached in memory. ③ Given inode number k, look up its address in the imap and read the newest inode. ④ From there, proceed exactly as a classic UNIX file system does: the inode's direct, indirect or doubly indirect pointers lead to the data blocks. OSTEP 43.7

Because the imap is cached, the only extra work LFS does on an ordinary read is one lookup in memory, and a read costs the same number of disk I/Os as in a typical file system. LFS makes writes fast without making reads slower. OSTEP 43.7

CARRYCR (fixed place, rewritten about every 30 s) → imap pieces (cached in memory) → inode → data. Once the imap is cached, a read costs what it costs in FFS.

§6

How do directories work, and why don't updates cascade up to the root?

main · readpapers: skip

FOR THE PAPERS · SKIPDirectories and the cascade of updates do not appear in the papers.

Figure 6. Top: OSTEP's file-creation example (43.8, redrawn) and the lookup of foo. Bottom: the recursive update problem. Storing inode numbers in directories, and addresses only in the imap, stops the chain after one step.

A path such as /home/remzi/foo needs directories, and in LFS a directory is what it is in a classic UNIX file system: a file whose data is a list of (name, inode number) pairs. Creating file foo in directory dir writes, in one segment, foo's data block, foo's inode, dir's new data block containing the pair (foo, k), dir's new inode, and an imap piece holding the new addresses of both inodes (Figure 6, top). OSTEP 43.8

Looking up foo then runs: the imap, usually cached, gives the address of dir's inode, A3; dir's inode points to its data block at A2; that block says foo is inode number k; the imap again gives k's inode at A1; and k's inode points to foo's data at A0. OSTEP 43.8

The imap also solves a deeper problem that every file system which never updates in place must face, the recursive update problem (Figure 6, bottom). When foo's inode is rewritten, it moves. If directories stored inode addresses, dir's entry for foo would have to change, so dir's data block would be rewritten and move, so dir's inode would move, so dir's parent would need a new entry, and so on all the way up to the root, for a change to one file. Because directories store inode numbers and only the imap stores addresses, the change stops at the imap: dir still says (foo, k), and only the imap entry for k changes. OSTEP 43.8

CARRYDirectories hold (name, inode number), never addresses. When an inode moves, only its imap entry changes; without the imap, every write would cascade up to the root.

§7

What becomes garbage, and how does the cleaner reclaim it?

main · readpapers: needed

FOR THE PAPERS · NEEDEDCleaning and its cost, page ③'s 1/(1−u) again. When a cache cleans its own log, the papers count the copies as ALWA, and Kangaroo §2.2 names LFS cleaning as the example. One difference matters: a cache may drop live data instead of copying it, so a log can evict a whole segment with no copies at all (FairyWREN's large-object log, WA 1×). Figure 14 in §12.4 sets the three ways side by side.

Figure 7. Top: the two garbage examples of OSTEP 43.9 (imap pieces omitted, as OSTEP does). Bottom: cleaning segment by segment; amber blocks are live, red blocks dead. The cost follows the same law as an SSD's garbage collection.

LFS keeps writing the newest version of everything to new places, so old versions pile up across the disk, and OSTEP calls them garbage. Figure 7, top, shows two cases. Overwriting block 0 of file k writes a new data block and a new inode, so the old data block and the old inode are both garbage. Appending block 1 instead writes the new block and a new inode; the old inode is garbage, but the old block 0 is still pointed to by the new inode, so it stays live. OSTEP 43.9

LFS could keep the old versions and let users restore earlier contents of a file, which would make it a versioning file system. It keeps only the newest live version instead, so in the background it must find the dead versions and free their space. This is cleaning, a form of garbage collection. OSTEP 43.9

Freeing single dead blocks would not help. The disk would fill with small holes between live blocks, and LFS would lose what it needs most, large contiguous free regions to write segments into. So the cleaner works segment by segment (Figure 7, bottom). It reads M partly used segments, works out which of their blocks are still live, writes just the live blocks into N new segments with N < M, and frees the M old ones for new writes. OSTEP 43.9

This is page ③ §2 almost word for word, with the segment in place of the erase block and the cleaner in place of the garbage collector. The arithmetic of page ③ §3 carries over unchanged. In Figure 7, 12 of the 18 old blocks are live, so u = 2/3, and every segment freed for new data cost two segments of copying, an amplification of 1/(1 − 2/3) = 3.

Two questions remain, which OSTEP names as mechanism and policy: how to tell which blocks in a segment are live (§8), and which segments to clean, and when (§9). OSTEP 43.9

CARRYOld versions become garbage. The cleaner reads M partly dead segments, writes their live blocks into N < M new ones, and frees whole segments. The cost law is page ③'s: u = live fraction, WA = 1/(1−u).

§8

How does the cleaner know which blocks are still live?

main · readpapers: skip

FOR THE PAPERS · SKIPThe papers keep liveness in their DRAM index instead; each entry of Kangaroo's log index has a valid bit (Kangaroo §4.2; §12.5).

Figure 8. The liveness check (OSTEP 43.10, redrawn), with OSTEP's pseudocode. The segment summary block, marked SS, sits at the head of each segment.

LFS adds a small structure at the head of every segment, the segment summary block. For each data block in the segment it records the block's inode number, which says what file it belongs to, and its offset, which says which block of the file it is. OSTEP 43.10

To decide whether the block at address A is live (Figure 8): ① read its entry in the segment summary, inode number N and offset T; ② look up N in the imap and read inode N, which may already be in memory; ③ look in the inode, or in one of its indirect blocks, for where it thinks block T of the file lives. If that is exactly A, the block is live. If the inode points anywhere else, this copy is dead and no longer needed. OSTEP 43.10

LFS also has a shortcut. When a file is truncated or deleted, LFS increases the file's version number and records the new number in the imap, and the segment records version numbers as well. If the version stored in the segment differs from the one in the imap, the block is dead, and the cleaner never has to read the inode. OSTEP 43.10

Compare the FTL (page ③ §2). There, the OOB note on a flash page says which logical block the page holds, and the page is live exactly when the map still points to it. The segment summary is LFS's OOB note, and the imap with the inode is its map.

CARRYLiveness: the segment summary says the block at A is (inode N, offset T), and the block is live exactly when inode N's pointer T still equals A. A version number kept in the imap short-cuts deleted files.

§9

Which segments should be cleaned, and when?

skim · figure + carrypapers: needed

FOR THE PAPERS · NEEDEDKeeping hot and cold data apart, so that some units die whole. The page marks this section skim, but for the papers read it in full: FairyWREN splits every set into a hot and a cold half, each with its own log, and groups data of similar lifetime into one erase unit (FairyWREN §5.1, §5.4; §12.6).

Figure 9. Why the original LFS cleans cold segments sooner and hot segments later (OSTEP 43.11). The fractions are illustrative.

When to clean is the easy half: periodically, during idle time, or when the disk is full and there is no choice. Which segments to clean is the hard half, and the subject of many papers. The original LFS paper separates hot segments, whose contents are being overwritten often, from cold ones, whose contents are stable (Figure 9). A hot segment is best left alone for a while: its blocks keep dying as newer versions are written elsewhere, so the longer the cleaner waits, the less it has to copy. A cold segment may hold a few dead blocks, but the rest will stay live, so waiting gains nothing and its free space stays locked up. Rosenblum and Ousterhout concluded that cold segments should be cleaned sooner and hot ones later, and built a heuristic to do that; later work found better policies (Matthews et al., 1997). OSTEP 43.11

In page ③'s terms, the policy chooses victims with a low u. A hot segment cleaned too early has u near 1 and costs dearly; the same segment cleaned later has u near 0. Grouping data by how soon it will die, the SSD rule of page ③ §10.1, is the same idea seen from the writer's side.

CARRYClean when idle or forced. Clean cold segments sooner and hot ones later: waiting lets hot segments empty themselves, which keeps u, and so the cost, low.

§10

What happens if the system crashes in the middle of a write?

main · readpapers: skip

FOR THE PAPERS · SKIPCrash recovery is not what the papers study. KVell, the one persistent store among them, keeps no commit log and acknowledges an update only once it sits at its final place (KVell §1). What a cache gives up by forgetting on restart: §12.8.

Figure 10. Crash recovery in LFS (OSTEP 43.12). Top: segments form a log, each pointing to the next. Bottom: the two checkpoint regions are written alternately, and a torn one is recognized by its mismatched timestamps.

During normal operation LFS buffers writes in a segment and writes the segment out when it is full or when some time has passed. The segments form a log: the CR points to a head and a tail segment, and each segment points to the next one to be written. LFS also rewrites the CR periodically. A crash can strike during either kind of write. OSTEP 43.12

A crash during a CR update. LFS keeps two CRs, one at each end of the disk, and writes them alternately. It writes each one carefully: first a header with a timestamp, then the body, then a final block with a timestamp. If the system crashes partway through, the two timestamps of that CR disagree, and LFS recognizes it as torn. On reboot it uses the most recent CR whose timestamps agree, so it always starts from a consistent CR (Figure 10, bottom). OSTEP 43.12

A crash during a segment write. The CR is rewritten only every 30 seconds or so, so the last consistent checkpoint may be old, and restarting from it alone would lose the last many seconds of updates. LFS instead rolls forward, a technique borrowed from databases. Starting from the last checkpoint, it finds the end of the log recorded in the CR, reads the segments written after it, and applies every valid update it finds, recovering much of the data and metadata written since the checkpoint (Figure 10, top). Rosenblum's dissertation has the details. OSTEP 43.12

This is page ② §7's map-recovery problem again. The FTL rebuilds its map after power loss by scanning the OOB areas, and higher-end SSDs speed that up with LFS's own tools, checkpoints and logs. OSTEP 44.7, aside

CARRYTwo CRs, written alternately, each with a timestamp at both ends; a torn CR is ignored. After a crash, start from the newest consistent CR and roll forward through the segments written since.

LFS's idea, write to unused space and reclaim the old space later by cleaning, is called shadow paging in databases and copy-on-write in file systems. Its large writes suit many devices. On a hard disk they minimize positioning; on RAID-4 and RAID-5 they avoid the small-write problem entirely; and on flash, He et al. found that large requests are needed for high performance, so an LFS-style file system may suit SSDs well. OSTEP 43.13

The price was cleaning, and cleaning became the centre of a long controversy. Seltzer et al. (1995) showed that LFS sometimes performs poorly, particularly for workloads with many fsync() calls, such as databases, and OSTEP suggests such concerns may have limited LFS's early impact. Mogul (1994) added that buffering writes for too long and then sending them in a big burst can hurt reads. OSTEP 43.13 and references [SS+95], [M94]

Yet the design lives on in NetApp's WAFL, Sun's ZFS, Linux btrfs, and the FTL inside flash SSDs (pages ② and ③). WAFL turned the flaw into a feature: by keeping old versions available as snapshots, it has to clean less often, and users can get back files they deleted by mistake. OSTEP's tip for this is "turn flaws into virtues". OSTEP 43.13 and its tip

CARRYLFS and the log-structured FTL are one design at two layers: append to fresh space, keep a map from stable names to current places, and clean. They share the costs too: cleaning traffic set by u, and a map that must be found again after a crash.

12.3 · The imap, and the cache's index

Figure 13. The imap, and the cache’s index. ① Every layer either computes a place or looks it up in a map that changes on every write. ② LFS can keep its whole imap in memory because it has one entry per file; a cache needs one per object. ③ The papers’ two answers: index only a small part, or keep the index on flash and cache its hot part, as LFS does with the imap.

① Figure 4 showed two ways to find an inode: compute its address, as a classic UNIX file system does, or look it up in the imap, which moves with every write. The SSD made the same choice between direct mapping and a page map (page ② §6–§7), and a flash cache makes it a third time: a set-associative cache hashes the key, a log-structured one keeps a DRAM index. ② LFS keeps its whole imap in memory because it needs one entry per file; a cache of billions of tiny objects needs one per object, page 3.5 §7's DRAM bill. ③ Kangaroo indexes only its small log, about 5% of the capacity, and computes the place of everything else. Nemo writes its index, groups of Bloom filters, to flash and caches the frequently used groups in DRAM, as LFS writes imap pieces into its log and caches them. Kangaroo §2.3 and §3 · Nemo §4.1 and §4.3

12.4 · Cleaning becomes eviction

Figure 14. Cleaning becomes eviction. The same segment, reclaimed by a file system (a) and by two kinds of cache (b, c); the arrows mark what is copied. WA counts writes per new object stored, as in page ③ §3: in (c), each freed segment takes five new objects for six writes. The grey line under each row names the papers that work that way.

A file system may not lose data, so §7's cleaner must copy every live block. A cache may: "since Kangaroo is a cache, not a key-value store, it is free to drop objects". Figure 14 reclaims one segment three ways: (a) copying every live object costs WA 3 at u = 2/3, Figure 7's number; (b) dropping the segment costs no copies but loses the popular object; (c) copying only what was read keeps it for WA 1.2. In LFS the workload sets u; in a cache u becomes a choice, traded against the miss ratio, and Flashield names the cost of the copies cache-level write amplification, CLWA. Kangaroo §1 · Flashield, NSDI 2019, §1 and §2.2

The papers sit at (b) and (c). FairyWREN's large-object log and CacheLib's large-object cache drop whole segments; Kangaroo re-admits objects read during their stay in its log, and Nemo writes hot objects back before it evicts a set-group. Where a unit holds carefully gathered sets, they copy everything live instead, since dropping a set raises the miss ratio. A key-value store must sit at (a), which is why Netflix's RocksDB flash cache needed 67% overprovisioning. Kangaroo §2.3 and §4.3 · Nemo §3.1 and §4.2 · FairyWREN §5.2 and §5.3

12.5 · Liveness: the same rule a third time

Figure 15. Liveness, the same rule a third time. In each row the map points at the new copy, so it is live, and nothing points at the old one, so it is dead. The note on the copy (LFS’s segment summary, the FTL’s OOB area) only tells the collector which map entry to ask; the cache asks its DRAM index directly. Addresses are made up for the drawing.

§8 read the segment summary to learn which inode and block a copy held, then asked that inode whether it still pointed there; page ③ §2 did the same with the OOB note and the page map. In both, a copy is live exactly when the map still points at it. The caches keep the rule and drop the note, since their map is in DRAM: each entry of Kangaroo's log index carries a valid bit, and FairyWREN's set store keeps an in-memory index of where each set lies, so its GC rewrites the sets that index still points at. Kangaroo §4.2 · FairyWREN §5.3

12.6 · Hot and cold, decided when writing

Figure 16. Hot and cold, decided when writing. ① LFS waits until cleaning to tell hot from cold; FairyWREN splits each set when writing, into two subsets in two logs. ② The arithmetic is FairyWREN’s: 8 KB on every insert, against 4 KB on every insert plus 4 KB every fifth. ③ The naming follows LFS: hot means often written.

① §9's LFS told hot from cold when cleaning; FairyWREN does it when writing. Each set is split into a subset for popular objects and one for unpopular objects, each in its own log; new objects from the small-object log go into the unpopular subset, and every n rewrites both are read, merged and split again by popularity. ② With n = 5 and 8 KB sets, a set's writes over five inserts fall from 40 KB to 24 KB, a 40% cut. ③ The paper calls the unpopular subset hot in LFS's sense: its objects are the likeliest to be evicted, so it is rewritten most. This is grouping by death time (page ③ §10.1), done by the cache. FairyWREN §5.4

12.7 · A log on a log

Figure 17. Two layers that both reclaim. ① On an ordinary SSD, the drive’s GC can copy a set just before the cache rewrites it, so the copy dies at once; the drive cannot know what the cache is about to replace, as with an untrimmed delete (page ③ §4). ② Fix a lines the layers up; fix b leaves one layer to reclaim for both, and pays off only when the cache folds its own writes into that GC.

① Figure 11 stacks a cache on an SSD whose FTL is itself a log, and each layer reclaims on its own. FairyWREN gives the worst case: the drive's garbage collection copies a set, and the cache then rewrites that set at once to admit new objects, so the copy dies; on an ordinary SSD the two writes cannot be merged. The drive cannot know what the cache is about to replace, as with the untrimmed delete of page ③ §4. ② A cache that writes its log in order lets the drive's blocks die in order, as CacheLib's FIFO does (12.2). For sets, a ZNS or FDP drive hands the erase to the cache, but that alone "just moves the GC from the device to the cache"; FairyWREN gains by folding its own writes into that GC, nest packing (page 3.5 §8.2). FairyWREN §4.4 and §5.3 · CacheLib §5.2 · tree node 1.3.3

12.8 · Crashes: what a cache may forget

Figure 18. Crashes: what a cache may forget. ① A file system must find all its data again. ② A cache may start empty, at the price of warm-up. ③ CacheLib’s warm restart keeps the map across a planned restart, as LFS’s checkpoint keeps it across a crash. ④ A store without a commit log pays at recovery instead. The step boxes are a sketch; the numbers are quoted.

① A file system must find its data after a crash, so LFS reads its newest consistent checkpoint and rolls forward (§5, §10). ② A cache may forget and restart empty, but its hit ratio climbs back slowly, and a large hybrid cache can take several days to warm up. Restarts are routine: 75% of CacheLib's lookaside caches and 95% of its CDN caches restart within seven days, to pick up code fixes. ③ CacheLib's warm restart keeps the map instead, as LFS's checkpoint does: on a planned shutdown the DRAM cache's state stays in shared memory, and the flash cache's index and Bloom filters are written to flash for the next process. ④ KVell, a store rather than a cache, keeps no commit log; after a crash it rescans all its slabs to rebuild its in-memory index, which can take minutes. CacheLib §3.7, §4.3 and §5.2 · KVell, SOSP 2019, §5.6

CARRYA log-structured flash cache is LFS a third time: segments sized by the erase unit, a DRAM index in the imap's place, eviction in the cleaner's. Its one new freedom, dropping live data, turns u from a property of the workload into a choice traded against misses. Liveness keeps the map rule; hot and cold go to separate logs; and stacked on an SSD, the two logs must be lined up (write in order) or merged (the cache does the GC).
