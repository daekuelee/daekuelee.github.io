3.5 Flash caches: how a cache finds a 100-byte object, and why that costs DRAM

Page ③ closed the SSD's own books: its FTL map and its garbage collection live inside the drive and cost little. This page opens a second problem, one layer up. Large services cache billions of objects of about 100 bytes, DRAM is too expensive to hold them, so the cache moves onto SSDs. An SSD takes only page numbers, so the cache needs a second map, from keys to pages, in the server's DRAM, and with objects 40 times smaller than a page that map costs more DRAM than the flash it points into. §0 states that problem against page ③; §1–§5 show how a cache finds an object; §6–§9 take the cost by why, what, how and when.

§0

Page ③ settled the SSD's map and its garbage. What problem starts here?

★ core · read every line문제 · 왜

Figure 0a. The problem as a chain. Steps ① to ③ are why a flash cache exists; ④ and ⑤ are why it needs a map that the SSD's FTL map cannot be; ⑥ is why that map is the cost. Teal is the SSD of pages ② and ③, violet the new map in the server's DRAM, red the cost. The right column is each step's evidence.

Page ③ closed the SSD's own books. Inside the drive, the FTL keeps a map from page numbers to chip locations, one 4-byte entry per 4 KB page: about 1 GB of controller DRAM per TB, 0.1% of the data. Garbage collection copies live pages at a cost of 1/(1−u), and overprovisioning keeps u down. Both costs belong to the drive and were kept low there. This page leaves that layer as it is and climbs to the software that uses the drive. page ③ §3, §5

That software is a cache. Large services put one in front of a slow database, and what it holds are billions of tiny objects: Facebook's social-graph edges average under 100 bytes, and tweets under 33 characters (Figure 0a, ①). Holding them in DRAM is fast and expensive: Flashield prices a 4.25 TB cache at $130,900 as seventeen DRAM servers and $12,500 as one server with four SSDs (②). So the cache moves onto flash, and keeps under 1% of its capacity in a DRAM cache of the hottest objects (③). Kangaroo §2.1, §3 · Flashield §1, Table 1 · CacheLib §4.2

Here the new problem starts. An SSD is a block device: it is asked to read or write logical page p, and nothing else. A read arrives with a key, and the FTL's map starts from logical page numbers, so it cannot say which page holds "user:42 friend:9" (④). The cache must answer that itself, with a map of its own from keys to places on flash, kept in the server's main memory so that finding an object costs no flash read of its own (⑤). This map is not the FTL map moved or copied: it sits above it, and every read passes through both, ① then ② in Figure 1.

The two maps have different owners, and nothing joins them into one. The cache's map ends at a logical address: the LBA of page ① §3, the number the SSD shows the outside. This page counts it in 4 KB pages; a drive formatted with 512-byte blocks numbers the same page 8 × 7,341 = 58,728, and the driver converts. Which physical page holds that address is decided by the FTL in the drive's firmware, and it changes whenever garbage collection copies the page (page ② §7); the cache never learns it. It does not need to: the cache chose p itself when it wrote the object, so it can record key → p, and the SSD promises that read(p) returns what was last written to p, wherever the page now lies on the chips. A program using virtual addresses is in the same position: it never sees a physical address, and the MMU and the OS keep the translation. So the cache's code does three things: it keeps and searches the key-to-logical map, it chooses the logical address each new object is written to (the end of a log, or the page a hash picks), and it sends read(p) and write(p). The logical-to-physical step is not in its code. Zoned SSDs move one decision across that line: the host picks which zone, an erase unit, its data goes into, though still not the chip location, and FairyWREN and Nemo use exactly that lever (page ③ §10.2, §8).

The unit makes it expensive. The FTL maps 4 KB pages; the cache maps objects about 40 times smaller, packed some 40 to a page, so its map needs one entry per object (§1). At 15 bytes per 100-byte object, the map is 15% of the data, and DRAM costs about ten times flash per byte, so the map's DRAM would cost about 150% of the flash it points into (⑥, derived in §7). The cache moved to flash to save DRAM, and its map spends the DRAM again.

Figure 0b. Page ③ against this page, row by row. The left column is what page ③ built inside the drive; the right column is the same question asked by the cache above it. Red marks what is new on this page; the rest is page ③'s trade at a smaller unit.

Figure 0b sets the two layers side by side. The trade is the one page ③ already met: a map entry per small unit costs memory, and placing by a fixed rule with no map costs rewrites. Page ③'s FTL answered with a hybrid, a few page-mapped log blocks in front of block-mapped data; Kangaroo answers the cache's version with a small indexed log in front of hashed sets (§5). Three things are new. The map is keyed by the application's keys, which the SSD never sees. The unit is about 40 times smaller than a page, so a per-object map has about 40 times more entries per byte than the FTL's, and a fixed-rule placement rewrites about 40 times more bytes than it stores (§3). And the two layers stack: the cache's own rewrites go down into the SSD, whose garbage collection multiplies them again (§8). page ③ §5, §6

So the problem this page and the papers take up fits in one sentence: find each of billions of tiny objects with a few bits of DRAM, without multiplying the flash writes that page ③ priced. Kangaroo's abstract states the first half as a limit: "very few bits per cached object can be kept in DRAM without losing flash's cost advantage." §1–§5 show the designs that find an object; §6–§9 measure the cost and follow the papers that cut it. Kangaroo, abstract

CARRYPage ③'s FTL map turns page numbers into chip locations, inside the drive, at 0.1% of the data. A flash cache is asked by key and the SSD takes only logical page numbers, so the cache keeps a second map, from keys to logical pages, in the server's DRAM; only the FTL turns those into physical pages. With ~100 B objects that map needs an entry per object and would cost more DRAM than the flash it points into: the cache fled DRAM, and its map brings DRAM back. It is page ③'s trade, map size against rewrites, one layer up, with a 40× smaller unit and write amplification that multiplies across the two layers.

§1

Why does a flash cache need a map of its own?

★ core · read every line문맥

Figure 2. Why the map has one entry per object. ① The object sizes Kangaroo §2.1 reports, on the scale of one 4 KB page; the amber bar is 700 B. ② Giving each object its own page wastes almost all of the flash, so caches pack about 40 small objects into each page. ③ A packed page holds many keys, and a read names a key, so the map from key to place needs an entry for every object.

§0 and Figure 1 set the scene: a read carries a key, the SSD takes only logical page numbers, and the cache's map ① turns the one into the other. The SSD keeps its own map ② from logical to physical pages, the FTL map of page ② §7 and page ③ §5; this section shows why the cache's map needs an entry for every object, where the FTL's needs one per page.

How many entries it needs depends on the objects (Figure 2, ①). The papers cache tiny ones: Facebook's social-graph edges average under 100 bytes, tweets average under 33 characters, and Azure's IoT sensor metadata averages 300 bytes. Kangaroo sums it up as "billions of objects that are each significantly less than the 4 KB minimum write granularity of block-storage devices". Kangaroo §2.1

A cache could give each object a 4 KB page of its own (②a). A 100-byte object would leave 97.5% of the page empty, and the same flash would hold 41 times fewer objects. So caches pack about 40 objects into each page (②b). A packed page holds 40 keys, and a read still arrives with one key and no page number, so the map needs an entry for every object (③). The SSD's map has one entry per page; the cache's has one per object.

CARRYThe SSD is asked by logical page number, the cache by key. Objects of about 100 bytes are packed some 40 to a page, so the cache's own map, kept in the server's DRAM, needs one entry per object, not per page.

§2

How does a log-structured cache find an object?

main · read문맥

Figure 3. A log-structured cache, from the question to the mechanism. The top band is the question. WHY A LOG: three flash rules from pages ② and ③ force three parts, a buffer, a log and an index. WHICH LOG: the same append-only idea as the FTL's log on page ② §7, one layer up, compared row by row; the three boxes are what changed, and the red one is §0's problem. HOW IT RUNS: one object traced through ① insert, ② buffer full, ③ lookup and ④ flash full. Keys and places are made up for the drawing.

The question. A new object of about 100 bytes arrives with only a key. Where on flash should it go, and how is it found again? Three rules from earlier pages decide it (Figure 3, WHY A LOG). a. Flash writes no less than a 4 KB page, so a 100-byte object written alone costs a whole page (§1, Figure 2). b. A page cannot be written over in place; its whole block must be erased first (page ②). c. Flash wants large, in-order writes; small scattered ones raise garbage collection's copying (page ③ §4). So the cache collects new objects in a buffer in DRAM (a), and writes each full buffer at the end of a log, never over old data (b, c). Once an object can be anywhere in the log, its place cannot be computed from the key, so the cache writes it down: one row per object, in an index in DRAM. That row is the entry per object of §1's Figure 2, ③.

Which log. "Log" here is not a file of messages. It is a way of placing data: append at the end, never write over. It is the idea page ② §7 called logging, used one layer up (Figure 3, WHICH LOG). The FTL appends 4 KB pages onto physical flash and keeps one map entry per page in the controller's DRAM. This cache appends 100-byte objects onto the logical pages the SSD exposes, and keeps one row per object in the server's DRAM. The two logs are stacked: the cache's segments reach the SSD as large in-order writes, and the FTL's own log still runs under them.

What moving up changed. Writes stay good: objects are packed and each is written once, in large runs. Eviction replaces garbage collection: a cache may forget, so when space runs out the oldest segment is simply dropped and nothing is copied, which is page ③ §10's panel ②, u = 0. DRAM gets worse: a row per 100-byte object instead of an entry per 4 KB page takes the map from 0.1% of the data to at least 15% (§7). So this design is not the fix. It is the plain design whose map is §0's problem, and §3–§8 are the ways out.

One object, traced. The bottom of Figure 3 runs user:42 friend:9. It goes into the buffer, and its row already names where the buffer will land: seg 7, byte 1,200 (①). When the buffer is full, it is written as seg 7 at the end of the log in one large write (②). A later get finds the row and reads that one place (③); before ②, the buffer itself answers. When the flash is full, the oldest segment, seg 0, is dropped whole, and the rows of its objects go with it (④); page ④ §12 sets this beside LFS's cleaning.

Flashield is built this way, and so is CacheLib's cache for objects of 2 KB and up, which writes regions in order and keeps every object's place in a DRAM index. A plain row, with a short hash tag in place of the key and pointers for the table and for eviction, takes over 15 bytes; Flashield squeezes it to about 30 bits, still about 37% of the flash bill (§7). Kangaroo §2.3 and §4.2 · Nemo §2.3 · CacheLib §4.2 · Flashield §1

CARRYA log-structured cache is the FTL's logging moved up to objects: writes stay cheap and eviction copies nothing, but the map needs a DRAM row per 100-byte object, at least 15% of the data. It is the design that has §0's problem, not its fix.

§3

How does a set-associative cache find an object without a map?

main · read문맥

Figure 4. A set-associative cache. Top: the key's hash names the set, and the set is one 4 KB page, so no map is needed. Middle: the rule that makes this work, against Figure 3: an object may live only in its own set. Lookup ①–③ reads one page. Insert ①–③ rewrites a whole 4 KB page for one small object. The bottom boxes are Figure 3's trade, reversed.

The idea. Do not remember where an object is; compute it. The flash is split into many small sets, each one 4 KB page, and a hash of the key picks the set. An object may live only in its own set, so the key alone says which page to read, and no row per object is needed (Figure 4, top).

The middle row of Figure 4 puts this rule against §2's. A log lets an object go anywhere, so the cache must remember where; sets let it go to one page only, so the cache can work out where. The ZNS paper calls the SSD's own page map "fully-associative" for the same reason: any page may go anywhere, so every page needs an entry (page ③ §10.2). It is the trade of page ③ §5's block mapping, one layer up: there, a page's place inside its block was computed, so the map shrank to one entry per block, and rewriting one page moved the whole block. Here the map shrinks to nothing, and adding one object rewrites the whole page.

A lookup hashes the key to its set, reads that one 4 KB page, and scans its 40 or so objects for the key (lookup ①–③). An insert reads the page, adds the object, dropping the oldest one if the page is full, and writes the whole page back (insert ①–③).

So the trade is §2's, reversed. DRAM is almost free: no rows, only a small filter per set (§4), about 3 bits per object in all. Writes are dear: one 100-byte object costs a 4 KB write, about 40 times its size, and the writes land on scattered pages, so whole blocks seldom empty out together (page ③ §4) and the SSD's own garbage collection copies more. CacheLib's cache for objects under 2 KB is built this way. Kangaroo §2.3 · CacheLib §4.2

CARRYA set-associative cache lets each object live only in the one page its key hashes to, so the place is computed and no map is kept; but adding one small object rewrites that whole 4 KB page, about 40 times the object.

§4

What is the Bloom filter in each set for?

main · read문맥

Figure 5. A Bloom filter, for one set. Every key in the set's page turned on 4 of the 64 bits. A lookup checks the same 4 positions for its own key. ① All four are 1: the key may be there, so the page is read. ② One is 0: the key was never added, so the read is skipped. The bit positions are made up for the drawing; the 8 bytes and 4 positions per key are CacheLib's (§4.2).

The idea. In §3, every lookup reads a page, even for a key that is not cached, and then finds nothing. A Bloom filter is a few bits in DRAM that answer, without touching flash, either "certainly not here" or "maybe here". CacheLib keeps one per set, 8 bytes, and reads the page only on "maybe". CacheLib §4.2

Figure 5 shows how it answers. Every key in the set's page has turned on 4 of the filter's 64 bits, at positions computed from the key's hash. A lookup computes the same 4 positions for its own key. If all four are 1, the key may be there, and the page is read (①). If any is 0, the key was never added, and the miss costs no flash read (②).

"Maybe" is sometimes wrong, because other keys can turn on the same bits; then one read is wasted, but the answer is never wrong. A filter cannot take one key back out, so it is rebuilt from the page whenever the page is rewritten. How many bits buy how few wrong "maybe"s is tree node 1.6.1. CacheLib §4.2, Figs. 10–11

CARRYA Bloom filter spends a few bits of DRAM per key to answer "certainly not here" or "maybe here", so a set cache reads flash only when the key may be there.

What does Kangaroo put together?

main · read문맥

Figure 6. Kangaroo combines Figures 3 and 4. KLog is small enough that its per-object index is cheap; KSet holds almost everything with no index. ① When an object leaves KLog, every KLog object bound for the same set leaves with it, so one 4 KB set write carries several new objects. ② When too few would go, the write is skipped. The idea. Use each design where it is cheap. Kangaroo states the dilemma of §2 and §3 in one line: "Log-structured caches require too much DRAM, and set-associative caches add too much write amplification." Its answer is a small log, KLog, about 5% of the flash, in front of a large set area, KSet, about 95% (Figure 6, top). KLog's index is cheap because KLog holds few objects, and KSet needs only filters. The shape is page ③ §6's hybrid mapping one layer up: a small area with an entry for every item, in front of a large area that needs far fewer. Kangaroo §2.3 and §3

New objects enter KLog first. When one has to move on to KSet, every KLog object bound for the same set goes with it, so one 4 KB set write carries several new objects instead of one (①). If too few would go, fewer than a threshold n, the write is not worth it: they are dropped, or kept in KLog if they were read there (②). Kangaroo §3 and §4.3

The result is 7.0 bits of DRAM per object, and set writes that carry several objects each: in the paper's own example, the cache writes 5.8 times the new data, against 17.9 for sets alone (this ratio, ALWA, is §8's). tree node 1.7.4 re-checks the example. Kangaroo Table 1 and §3

§6

Why is DRAM the cost to fight?

main · read왜 · in detail

Figure 7. Why DRAM is the cost to fight. Top: Flashield prices one cache size both ways. Below: three costs that the price tag leaves out, ① to ③. The violet box is the plan every paper starts from, and the reason the map of Figure 1 ① must stay small.

§0 used the price tag as step ②; this section gives its source and the three costs the tag leaves out. Holding everything in DRAM is the fast way and the expensive one. Flashield prices a 4.25 TB cache both ways (Figure 7, top): seventeen servers with 256 GB of DRAM each cost $130,900, while one such server with four 1 TB SSDs costs $12,500, more than ten times less. Eisenman et al., Flashield, NSDI 2019, §1 and Table 1

Three more costs sit on top of the price tag. The gap keeps widening: over 2013–2023, flash prices fell about 14×, DRAM's only about 2× (①). DRAM draws power all the time, up to half of a server's, and makes up 40–50% of a server's cost (②). And DRAM is not a dial a cache can turn up: operators run a few standard server configurations, every service on the machine wants memory, and Facebook's trend has been less DRAM and more flash per server (③). McAllister et al., FairyWREN, OSDI 2024, §2 and Fig. 2 · Kangaroo §2.2

So a flash cache keeps its data on flash and keeps in DRAM only what finds the data: the map of Figure 1 ①. Kangaroo states the limit in its abstract: "very few bits per cached object can be kept in DRAM without losing flash's cost advantage." OpenStd's founder gives the same reason for the company: RAM has become very expensive, so the cache moves onto SSDs, with algorithms that keep it as fast as RAM. Kangaroo, abstract · Maeil Business Newspaper interview, 2026-10-05

CARRYDRAM costs about ten times flash per byte, draws power all the time and is fixed per server. So a flash cache keeps only its map in DRAM, and that map has to stay small.

  1. An index holds one entry per thing it finds.N objects need N entries of e bytes each: N × e bytes of DRAM. §1 showed why the cache's map has an entry per object, not per page.

How do the papers cut the bill?

★ core · read every line문제 · how

Figure 9. How the papers cut the bill. ① A set cache on an ordinary SSD: the cache's factor and the SSD's factor multiply, so one byte of new objects costs about 80 bytes of flash writes (Kangaroo §2.3; DLWA 2 is an example). ② The four caches as a chain: each red line is the problem the next row takes up. 8.1 · Writes multiply across the two layers (Figure 9, ①)

Cutting DRAM with sets costs writes, and the papers count writes in two layers. ALWA, application-level write amplification, is the cache rewriting its own data: a whole 4 KB set for one object (§3), or its own cleaning when its log fills (page ④ §12). DLWA, device-level, is the SSD's garbage-collection copies beneath that, page ③'s 1/(1−u). They multiply, because the SSD amplifies whatever the cache sends it. A set cache at ALWA 40 on a drive at DLWA 2 programs about 80 bytes of flash per byte of new objects, so by page ③'s Figure 3 it gets 1/80 of the drive's erase budget and 1/80 of its write speed. Sets also raise the DLWA itself, because their writes are small and random. CacheLib's production numbers show both layers: its small-object cache measures ALWA about 6.5× and DLWA 1.1–1.4×, and keeps the DLWA that low only by leaving the flash 50% overprovisioned, which its authors call an open challenge. Kangaroo §2.2 and §2.3 · FairyWREN §3.3 · CacheLib §5.2, "Flash endurance"

8.2 · Each paper fixes what the design before it left (Figure 9, ②)

Flashield stays log-structured (§2) and cuts writes at the door. New objects wait in DRAM, and a small classifier sends to flash only those predicted to be read again before they change, so many objects are never written at all. Its index is compact, about 30 bits per object by Kangaroo's count, but still one entry per object, so its DRAM grows with the flash. tree node 1.7.2. Flashield §1 · Kangaroo §2.3

Kangaroo is §5's design: 7 bits per object and a fraction of the sets' ALWA. What it leaves is the write pattern: every set write is still a random 4 KB write, the worst case for DLWA. tree node 1.7.4. Kangaroo §3 · FairyWREN §3.3

FairyWREN takes that up. It moves to SSDs with a Write-Read-Erase interface, ZNS or FDP, where the host places data into erase units and erases them itself, so page ③ §2's collector now runs inside the cache. A set that the collector must copy anyway can then take its waiting log objects in the same write ("nest packing"), and objects with different lifetimes go to different erase units, page ③ §10.1's grouping by death time (page ④ §12.6). Its claim: 12.5× fewer flash writes than Kangaroo. tree node 1.7.5; zoned SSDs in tree node 1.3.3. FairyWREN §1, §4.3, §5.1 and §5.3

Nemo re-measures FairyWREN on a commercial ZNS SSD and finds total WA above 15× on a Twitter trace, after fixing bugs in FairyWREN's released code that kept most objects from ever reaching the sets. The cause is the number of sets: with so many, a set write carries only one or two new objects, and a set is about 7% filled by new data when it is written. Nemo hashes into a few large set-groups held in DRAM, fills them to about 89%, then writes each group whole and later evicts it whole, so no old set is ever read back and rewritten: page ③ §6's switch merge in place of the partial one. WA 1.56 and DLWA about 1, at 8.3 bits per object, with Bloom filters as the index, kept partly on flash (page ③ §7's idea, and LFS's: page ④ §12.3). tree node 1.7.6. Nemo §1, §3 and §4.1

KVell works on another axis. It is a persistent key-value store, not a cache, and its finding is that on NVMe drives the CPU, not the drive, is the bottleneck. So each core owns its own slice of the data and needs almost no synchronization, I/O is sent in batches, and nothing is kept sorted on disk. tree node 1.7.1. Lepers et al., KVell, SOSP 2019, §1

CacheLib is Meta's production engine under most of this: the size split of §9, a DRAM cache in front, and admission policies that limit flash writes. Kangaroo, FairyWREN and Nemo are each built as a CacheLib module. tree node 1.7.3. CacheLib §4.2 · Kangaroo §1 · FairyWREN §1 · Nemo §1

§7's formula depends on the object size, so Figure 10 ① plots it. A map with 15 bytes per object costs as much DRAM as the flash it maps at objects of about 150 bytes, about 7% at 2 KB, and under 1% only above about 15 KB. Filters at 3 bits per object stay under 4% even at 100 bytes. CacheLib draws its line at 2 KB for this reason. Above it, "the number of unique objects in a LOC will only number in the millions. It is therefore feasible to keep an in-memory index". Below it, "billions of small objects can fit on a single 1TB flash device", and "an exact lookup index … would use an unreasonably large amount of DRAM". So its large-object cache (LOC) keeps a full map, and its small-object cache (SOC) is sets with filters. CacheLib §4.2 · arithmetic on Nemo §2.3

Writes become the limit when the flash is dense and must last (②). Packing more bits into each cell puts more data on the same silicon, with less carbon per bit, but each cell survives fewer erases. FairyWREN computes that a 2 TB QLC drive kept for six years allows the application only 14 MB/s, 0.09% of the drive's write bandwidth, and that for ten years QLC allows fewer than 0.37 drive writes per day, while Kangaroo, in FairyWREN's evaluation, performs 1.46: about four times the budget. On such flash, writes decide, not DRAM. FairyWREN §1 and §3.3, Fig. 4

The papers' common answer is about when to write at all: a flash write is worth making only when much of it is new (③). A plain set cache writes 4 KB to add 100 bytes, 2.4% new. Kangaroo admits to a set "only when there are enough hash collisions — i.e., only when the flash write is sufficiently amortized"; with a threshold of 2, that cut flash writes by 32.0% for 6.9% more misses. Nemo measured FairyWREN's sets at about 7% new when written, and fills its own set-groups to 89.34% before writing them. Kangaroo §1 and §5.4 · Nemo §1 and §4.2

CARRYA per-object map is the limit when objects are small: below 2 KB, CacheLib switches to sets. Writes are the limit when flash is dense and must last years: QLC allows under 0.37 drive writes per day. The papers' answer to both is to write a set only when most of it is new.
