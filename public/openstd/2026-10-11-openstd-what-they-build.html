OpenStd 가 만드는 것: SSD 위의 cache, 그리고 "10x cost efficiency" 가 나오는 자리

대표님은 무엇을 만드는지 직접 말씀하셨다. "캐시는 … 보통 램(RAM)을 많이 활용했는데, 이제는 램 가격이 매우 비싸졌다. 그래서 우리는 솔리드스테이트드라이브(SSD)를 활용해 캐시 데이터베이스로 활용하면서, 램과 같은 성능을 내도록 하는 알고리즘을 설계하고 있다." OpenStd 사이트는 OpenKache 를 "a high-performance cache server designed for modern SSDs" 라고 소개한다. 채용 페이지는 target workload 에서 10x cost efficiency 를 목표로 걸고 논문 다섯 편을 든다. 이 페이지는 10× 가 어디서 나오는지, 무엇이 그것을 깎는지, 왜 Rust 와 io_uring 인지를 차례로 보인다. 3.5 는 §3 까지만 필요하다.

첫째 전제는 DRAM 이다. Redis 와 Memcached 같은 in-memory cache 는 모든 object 를 DRAM 에 둔다. 대표님이 OpenStd 를 세운 이유도 DRAM 이 비싸졌다는 것이다. 3.5 §0 은 이것을 숫자로 봤다. 4.25 TB cache 는 DRAM 으로 $130,900 이고 SSD 로 $12,500 이다. 매일경제 2026-10-05 · Flashield §1, Table 1 (3.5 §0, §6)

둘째 전제는 write 다. block interface 에 맞춘 software 는 4 KB page 를 아무 데나 쓰고 GC 는 drive 에 맡긴다. 페이지 ③ 은 그 비용을 drive 안에서 셌다. 3.5 §3 의 set-associative cache 는 100 B object 하나 때문에 4 KB set 전체를 다시 쓴다. flash 는 erase 마다 닳는다. 그래서 write 는 공짜가 아니라 예산이다. 새 drive (ZNS, FDP) 는 data 가 들어갈 erase unit 을 host 가 고르게 한다. FairyWREN 과 Nemo 가 이 손잡이를 쓴다. 그림 2b 위가 두 층의 곱셈과, 세 논문이 그중 어느 칸을 줄이는지를 보여 준다. 페이지 ③ §10.2 · 3.5 §3 · 3.5 §8.2

셋째 전제는 CPU 다. KVell 의 abstract 가 그대로 말한다. "Logic to avoid random accesses, expensive operations for keeping data sorted on disk, and synchronization bottlenecks make these KVs CPU-bound on NVMe SSDs." drive 는 더 이상 느린 쪽이 아니다. software 가 스스로 하는 관리 작업이 느린 쪽이 됐다. KVell 이 잰 drive 의 write IOPS 는 2013 년 SATA SSD 의 11K 에서 2018 년 Optane 의 550K 로 50 배 늘었다. 그래서 core 하나가 I/O 하나에 쓸 수 있는 시간은 91 µs 에서 1.8 µs 로 줄었다 (그림 2b 아래). 예전에는 drive 를 기다리는 시간 뒤에 숨어 있던 정렬, lock, system call 비용이 이제 드러난다. CARRY"따라가지 못한다" 는 전제 셋이다. data 는 DRAM 에 있어야 한다는 전제, write 는 drive 가 알아서 한다는 전제, I/O 당 CPU 는 싸다는 전제다. NVMe flash 가 셋을 다 깼다. 깨진 전제 하나가 청구서의 한 몫이 된다. map 에 드는 DRAM, write 때문에 사는 flash, CPU 때문에 사는 server 다.

§1

"10x cost efficiency" 는 어디서 나오고, 무엇이 그것을 깎나?

그림 1 이 이 절의 그림이다. 두 cache 에 같은 단위로 값을 매기고, 그 결과에서 조건 셋을 읽는다.

  1. bytes 에 값을 매긴다.크기 s bytes 인 object 를 모아 모두 D bytes 를 cache 한다. flash 는 byte 당 p 이고, DRAM 은 byte 당 r·p 다. Flashield Table 1 은 실제 4.25 TB cache 의 r 을 준다. $130,900 ÷ $12,500 ≈ 10.5 이므로 r ≈ 10 이다. Flashield §1, Table 1 (3.5 §0, §6)
  2. DRAM cache.모든 byte 가 DRAM 에 있다. 그래서 C₁ = r·p·D 다. 그림 1 의 ① 행, 10 unit 이다.
  3. flash cache 는 청구서가 둘이다.하나는 flash 다. cache 는 o·D bytes 의 flash 를 산다. o = 산 flash ÷ live object 가 든 flash 이므로 o ≥ 1 이다. 다른 하나는 map 이다. object 는 D/s 개이고, 각각 DRAM 에 e bytes 의 map 이 필요하다 (3.5 §1). 그래서 map 값은 r·p·(D/s)·e 다. 둘을 더하면 C₂ = p·D·(o + r·e/s) 다.
  4. 나눈다.C₁ ÷ C₂ = r ÷ (o + r·e/s) 다. 분모의 두 항은 0 이상이고 o ≥ 1 이므로, 이 비율은 r 을 넘지 못한다. 비율이 r 이 되는 것은 o = 1 이고 e = 0 일 때뿐이다. 10× 는 가격비가 정한 상한이다. 설계 선택은 거기서 깎기만 한다.
  5. 조건 ①, map.object 100 B 당 map 이 15 B 이면 (3.5 §0) e/s = 0.15 이고 r·e/s = 1.5 다. 비율은 10 ÷ 2.5 = 4.0 이고, 이것이 ② 행이다. Kangaroo 의 7.0 bits 는 object 당 0.875 B 다. 그러면 r·e/s = 0.0875 이고, 비율은 10 ÷ 1.0875 ≈ 9.2 다. 이것이 ③ 행이다. 4× 와 9× 를 가르는 것은 map 크기이고, map 크기는 object 당 bits 하나로 정해진다. 3.5 §0, §5
  6. 조건 ②, write.o 는 write 때문에 cache 가 live object 없는 flash 를 가져야 할 때마다 커진다. 첫째 경로는 여유 공간이다. flash 를 비워 두면 GC 가 덜 copy 한다 (페이지 ③). CacheLib 은 50% overprovisioning 으로 device write amplification 을 낮춘다. 산 flash 의 절반이 비어 있으면 o = 2 이고, 비율은 10 ÷ 2.0875 ≈ 4.8 이다. 이것이 ④ 행이고, 큰 map 만큼 나쁘다. 둘째 경로는 마모다. flash 는 정해진 횟수만큼만 erase 를 견딘다. ALWA × DLWA 가 그 예산을 일찍 태우면, 같은 기간에 drive 를 다시 사야 한다. 이것은 시간에 퍼진 o 다. 3.5 §3 의 set cache 는 저장한 byte 당 약 40 bytes 를 flash 에 쓰므로 이 경우다. 페이지 ③ §3–§4 · 3.5 §3, §8.1
  7. 조건 ③, CPU.이 공식은 bytes 를 세고 server 를 세지 않는다. DRAM cache 는 server 당 DRAM 이 고정이라 여러 server 에 퍼진다. Flashield 의 DRAM 안은 server 17 대이고, SSD 안은 1 대다. 그 server 들을 대신하는 flash cache 는 더 적은 machine 으로 같은 초당 요청을 받아야 한다. server 가 두 배 필요하면 server 값이 돌아온다. KVell 의 발견은 NVMe 위에서는 drive 가 아니라 software 가 먼저 바닥난다는 것이다. Flashield Table 1 (3.5 §6) · KVell abstract

그러므로 10× 는 r 이다. flash cache 는 세 조건이 함께 설 때만 그것을 지킨다. object 당 몇 bits 의 map (e/s → 0), flash 를 적게 비우고 적게 닳게 하는 write (o → 1), server 당 충분한 초당 요청이다. 채용 페이지의 논문 다섯 편은 각자 이 셋 중 하나를 맡는다 (§2).

CARRYDRAM cache ÷ flash cache = r ÷ (o + r·e/s) 이고, r ≈ 10 이다. 상한은 가격비다. map (e/s), write (o), server (CPU) 가 각각 그 값을 끌어내린다. map 15 B 면 4× 가 남고, 7 bits 면 9.2× 가 남는다. flash 절반을 비우면 9.2× 가 4.8× 로 돌아간다.

그림 3. 논문 다섯 편과 §1 의 조건 셋. 논문마다 한 열을 맡고 나머지는 둔다. 보라 줄은 OpenStd 가 자기 server 를 소개한 말이다. 숫자는 3.5 §8 에서 가져왔고, 3.5 §8 이 논문마다 출처를 단다. 구조는 3.5 §4–§9 에 있다.

열을 따라 내려가며 읽는다. cache 논문 넷은 ① 과 ② 를 맡는다. Flashield 는 입구에서 write 를 줄이지만 object 마다 map entry 를 하나씩 둔다. Kangaroo 는 map 을 7.0 bits 로, rewrite 를 5.8 로 낮춘다. CARRYFlashield, Kangaroo, FairyWREN, Nemo 는 map (e/s) 과 write (o) 를 줄인다. KVell 은 CPU 가 한계가 되지 않게 한다. OpenKache 의 소개도 같은 셋을 부른다. DRAM-resident index, NVMe-backed data, core 사이의 최소 공유다.

왜 Rust, io_uring, QUIC, Redis protocol 인가?

그림 4. I/O 를 기다리는 두 방식. 왼쪽은 webserv event loop 의 readiness 방식이다. "이 fd 가 준비됐나?" 를 묻고, socket 에는 맞지만 disk file 에는 안 맞는다. 오른쪽은 completion 방식이다. program 이 요청을 줄 세우고 결과를 거둔다. Windows 의 IOCP 와 Linux 의 io_uring 이 이 방식이다.

webserv 에서 출발한다. webserv 의 event loop 는 epoll 이나 kqueue 에 어떤 fd 가 준비됐는지 묻는다. 이 물음은 bytes 가 스스로 오는 socket 에 맞는다. disk 는 요청받기 전에는 아무것도 하지 않는다. Linux 의 epoll 은 regular file 을 아예 거부한다 (EPERM). 그래서 readiness loop 에서 disk read() 는 device 접근 내내 thread 를 막고, I/O 하나에 system call 하나를 쓴다 (그림 4 왼쪽). KVell 이 잰 CPU 비용이 이것이다. drive 는 요청 여럿을 동시에 받을 수 있는데, software 가 그것을 하나씩 내느라 cycle 을 쓴다. io_uring 은 물음을 queue 로 바꾼다 (오른쪽). program 은 kernel 과 공유하는 ring 에 요청을 쓰고, 결과는 두 번째 ring 으로 돌아온다. 그래서 system call 하나로 batch 를 내고, polling mode 에서는 그것도 필요 없다. Windows 에서 IOCP 가 주는 모델이 이것이다. man 2 epoll_ctl · Axboe 2019 · KVell §1

CARRYio_uring 은 kernel 자신의 batch 로 조건 ③ 에 답한다. 요청을 넣고 결과를 거두며 system call 은 적다. webserv 의 epoll 은 file 을 기다리지도 못한다. Rust 는 C++ 의 memory 통제와 GC pause 없음을 주고, data race 를 거부하는 compiler 를 더한다. 이것은 공유 없는 code 와 AI 가 쓴 code 에 맞는다. QUIC 은 client 연결의 tail latency 를 지키고, RESP 는 Redis 사용자가 넘어오게 한다.
